Connecting your real GPS and UAV

Your GPS is currently breadboarded with no protocol locked in, and the airframe flies manually today with autonomous mode planned for later. Here's the path from where you are to a live site — you don't need to decide everything now, just the next step.

Breadboard GPS -> microcontroller -> bridge -> WebSocket -> this site (raw NMEA) (Arduino / ESP32) (parses) (ws://...) (telemetry.js)

This is the fastest way to get your breadboarded GPS talking to the site as-is, no new hardware needed. Your GPS module already outputs NMEA sentences over serial — you just need something reading that serial port and re-broadcasting it as JSON the site can consume.

Wire the GPS to any microcontroller with USB

An Arduino Uno or ESP32 is enough — GPS TX to the board's RX pin, GND to GND, 3.3V/5V per your module's spec. If it's already breadboarded this way, you're set.

Run a small Python bridge on your laptop

It reads the serial port, parses the NMEA line, and re-broadcasts lat/lng/battery as JSON over a local WebSocket at ws://localhost:8765:

pip install pyserial pynmea2 websockets

# bridge.py
import asyncio, serial, pynmea2, websockets, json

PORT = "/dev/ttyUSB0"   # or COM3 on Windows
clients = set()

async def read_gps():
    ser = serial.Serial(PORT, 9600, timeout=1)
    while True:
        line = ser.readline().decode(errors="ignore").strip()
        if line.startswith("$GPGGA"):
            msg = pynmea2.parse(line)
            payload = json.dumps({
                "lat": msg.latitude,
                "lng": msg.longitude,
                "batteryPct": 100,       # wire up a real reading when you have one
                "speedKmh": 0,
                "headingDeg": 0,
            })
            for ws in list(clients):
                await ws.send(payload)
        await asyncio.sleep(0.5)

async def handler(ws):
    clients.add(ws)
    try:
        await ws.wait_closed()
    finally:
        clients.discard(ws)

async def main():
    async with websockets.serve(handler, "localhost", 8765):
        await read_gps()

asyncio.run(main())

Flip one switch in the site

Open js/telemetry.js and set USE_LIVE_FEED = true. Every page — Connect, Delivery, Rescue — starts reading real coordinates instead of simulated ones. Nothing else changes.

If your GPS ends up on an ESP32 (it has WiFi built in), you can skip the laptop entirely — the board parses its own NMEA data and serves it directly to your phone or laptop on the same network. Good once you want the site working away from your desk.

Flash the ESP32 with a small web server

Using TinyGPS++ to parse NMEA and ESPAsyncWebServer (or the built-in WebSockets library) to serve the same JSON shape as the laptop bridge above — {lat, lng, batteryPct, speedKmh, headingDeg}.

Point the site at the board's IP

In js/telemetry.js, set WS_ENDPOINT to the ESP32's address on your WiFi network (e.g. ws://192.168.1.42:81), then set USE_LIVE_FEED = true.

You mentioned wanting both manual and automatic flight. Manual works today with no autopilot at all — the site just draws whatever path you click, and displays whatever position your GPS reports. Automatic waypoint flight is a separate step: it needs a flight controller that can actually steer to a coordinate, not just report one.

Add a real autopilot when you're ready

ArduPilot or PX4 running on a Pixhawk-class board is the standard choice — it's what accepts a waypoint and actually flies to it, with the failsafes (geofence, return-to-launch on signal loss) that manual flight doesn't have.

Bridge MAVLink instead of raw NMEA

Tools like mavsdk-server expose the same kind of JSON-over-WebSocket feed as paths 1 and 2 — so telemetry.js doesn't need to change shape, only where WS_ENDPOINT points.

Auto-routed waypoints only actually fly themselves once a real autopilot is in the loop. Until then, "automatic" on this site plans the route and shows you the numbers — you still fly it, or the human at the controls does.
Safety, before any of this flies outdoors

A geofence, return-to-launch on signal loss, and a pre-arm checklist aren't optional extras once real hardware is involved — they're what keeps a bug in this code from becoming a flyaway. Wire those into your flight controller before your first real flight, regardless of which integration path you take.
